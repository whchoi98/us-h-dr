# ADR-002: Restrict LBC-Managed ALBs via Ingress Annotations, Not CLI

## Status
Accepted (2026-11-11)

## Context
On 2026-11-11 AWS raised `DyePack.SpringBootActuatorMisconfigurations` on the ENI of
`k8s-ui-uiingres-*` (usw-eks). The Retail Store UI (Spring Boot) Ingress ALBs on all
three clusters were reachable from `0.0.0.0/0:80` and forwarded `/actuator/*`
(`/actuator`, `/actuator/prometheus`, `/actuator/metrics` returned 200).

`shared/demo/scripts/deploy-lbc-and-app.sh` had tried to lock the ALB down after
creation by revoking `0.0.0.0/0` and authorizing the CloudFront prefix list with the
AWS CLI, and the CloudFront CFN template added the same rule. Neither held.

## Root Cause
The ALB security group `k8s-<ns>-<ingress>-*` is **owned by the AWS Load Balancer
Controller**. LBC rebuilds the desired model from the Ingress on every resync
(observed every ~10h) and reconciles SG rules to it. The Ingress had no access-control
annotations, so the desired state was the default `inbound-cidrs: 0.0.0.0/0`: LBC
re-added `0.0.0.0/0` and removed the out-of-band prefix-list rule. The
`X-Lab-Secret` origin header was also never validated by any listener rule.

## Decision
All access control for LBC-managed ALBs is expressed as Ingress annotations, applied
together with the Ingress (kustomize overlay generated by `deploy-lbc-and-app.sh`):

| Concern | Mechanism |
|---|---|
| Only CloudFront may reach the ALB | `alb.ingress.kubernetes.io/security-group-prefix-lists: <com.amazonaws.global.cloudfront.origin-facing>` (without `inbound-cidrs`, LBC drops the `0.0.0.0/0` default) |
| Actuator not exposed | `/actuator` Prefix path inserted **before** `/`, backed by `actions.block-actuator` fixed-response 404 |
| CloudFront | `shared/demo/cfn/cloudfront-ui.yaml` — distribution only, no SG rule (a duplicate of the LBC rule would fail stack creation) |

The script fails closed: it aborts if the prefix list cannot be resolved, if the
overlay does not render with the restriction, or if the ALB SG still allows `0.0.0.0/0`.
`shared/scripts/cloudfront-protection.sh` refuses SGs tagged `elbv2.k8s.aws/cluster`.

## Alternatives Considered
- **App-level `management.endpoints.web.exposure.include=health`** — rejected: pods are
  scraped at `/actuator/prometheus` (`prometheus.io/scrape` annotation, CloudWatch agent).
  ALB-level blocking leaves pod-direct scraping and ALB health checks (target-direct)
  untouched.
- **Custom SG via `alb.ingress.kubernetes.io/security-groups`** — rejected: the SG would
  live outside both LBC and IaC lifecycles and orphan on teardown, blocking VPC deletion.
- **Keep CLI edits, re-run periodically** — rejected: races with LBC, exposure window.

## Consequences
- Never modify LBC-owned ALB/SG/listener resources with the CLI or CFN.
- `aws_lab_infra` base manifests stay unmodified; the hardening lives in this repo.
- Not addressed: origin custom-header validation (any CloudFront distribution can still
  reach the ALB via the prefix list). Add `alb.ingress.kubernetes.io/conditions.ui`
  with a non-guessable secret if required.
- `shared/scripts/deploy-app.sh` (nginx sample) still creates an unrestricted
  internet-facing ALB; it has no CloudFront path, so restricting it changes behavior.
